## Findings

1. **P1 — stale RPC head can pass freshness checks.** `packages/ens/src/authorize.ts` reads `latestBlock.timestamp` but only compares it with name expiry; it later stamps `checkedAt` using the current local time. A stalled RPC serving an old pre-revocation latest block therefore produces a freshly stamped authorization that passes the policy's 30-second age check. Require a bounded age/future skew for the latest head before an active authorization can be returned. Do not apply the same age limit to finalized head, since finality legitimately lags. Regression: both snapshots say active and expiry is future, latest timestamp is old, local now is current; result must fail closed.

2. **P2 — current EAC grants are not part of active authorization.** `HumanOSRegistrar.sol:382` computes active from local revoked flags, hierarchy, expiry, resolver and owner. `packages/ens/src/authorize.ts:118` independently checks resolution/capability/root records but never checks the resolver's effective `ROLE_SET_TEXT` grants on `keccak256('humanos.status')` and `keccak256('humanos.receipt')` for the agent account. Thus a snapshot with a missing scoped grant still yields active and nonempty capabilities. Add official `hasRoles` reads at both finalized/latest pinned blocks and fail closed when either grant is absent. This is an explicit requirement gap; the current registrar couples its exposed revocation operation to the revoked flag, so I am not claiming an ordinary agent can independently revoke admin-held grants through the current contract surface. Regression should nonetheless model EAC removal separately from registrar flags to enforce the requested intersection.

## ENS checks that look sound

The registrar uses official factory-deployed UserRegistry and PermissionedResolver proxies. Root/agent labels are single-use; capabilities only narrow and reject unknown bits. Parent/root/agent expiry is intersected, lifecycle flags remain authoritative, root revocation loops over a bounded64 agents, and expired names cannot be renewed back into service. Name-holder transfer/resolver/subregistry/upgrade powers are not granted. Canonical parent pointers are set and corresponding admin roles removed.

Dedicated resolver per identity makes resolver-wide key grants effectively confined to that identity's resolution. Official PermissionedResolver.decodeSetter derives the SET_TEXT resource from the key, matching the registrar's grant and revoke resource calculations. Agent grants are restricted to status/receipt; capabilities/root records remain controller-owned. Status text itself is intentionally not authority because agents can write it. Revocation removes scoped record grants and unregisters active names. The reader intersects finalized and latest capabilities, so latest revocation/narrowing blocks before finality; newly expanded state cannot acquire authority before finality.

Resolver permissions themselves are not time-expiring: raw writes to an expired name's dedicated resolver may remain possible until explicit revocation, while public resolution and HumanOS authorization are inactive. This does not by itself authorize external execution; avoid claiming the raw resolver's EAC grants automatically expire.

## Final writer/adapter follow-up (read-only, Claude still owns package)

Additional findings from current writer and adapter:

- **P1, mid-read revocation is knowingly returned as active.** `packages/ens/test/authorize.test.ts:183` starts a revoke after latest/finalized block numbers are fixed but before pinned state reads, then at line216 expects active:true. `authorize.ts:168` captures heads once and never checks whether latest advanced before returning. A revocation can therefore be mined before the execution caller receives an active result. Keep consistent pinned reads, then re-read latest head uncached: if its hash/number changed, bounded retry or fail closed. Test must expect revoked or unavailable in this mid-read scenario. This narrows a detectable race; off-chain side effects still cannot be atomic with arbitrary future chain transactions.
- **P2, root retry checks too little.** `register.ts:185` and catch199 recognize only rootId-to-node equality. They ignore root revoked/expired state, actual owner and requested expiry, returning successful idempotency for different parameters or dead names. Strict writer retry matching should validate identity, owner, requested expiry and live hierarchy identically in fast path and catch. Adapter can explicitly reuse a validated live root with its actual expiry, rather than claiming an attempted different expiry was applied.
- **P2, agent retry fast path/catch diverge.** `register.ts:232` checks root/account/capabilities/revoked but omits requested expiry and active lifecycle. Catch252 weakens this further by omitting rootNode and revoked entirely. An expired matching agent passes fast path; a revoked matching agent appearing during the transaction failure passes catch. Share one exact-match predicate across both paths, including active, !revoked, rootNode/name, account, capability bitmap and agentExpiry (not min effective expiry) equal requested seconds. Existing contract single-use labels prevent actual on-chain resurrection, but writer must not report success for unusable/differently bound identity.
- **P2, registration root arguments can disagree.** `register.ts:228` derives the returned node from rootLabel while registerAgent calldata uses independent input.rootNode at243. Validate rootLabel normalization and `nodeOf(rootLabel+'.'+parentName)===rootNode` before simulation. Otherwise caller can register under one root and receive a node for another. Current higher-level adapter passes consistent fields; the exported writer should enforce the invariant itself.
- **P2, funding bypasses nonce serialization.** `adapter.ts:75–78` reads balance and calls operator.wallet.sendTransaction outside `register.ts:withAccountLock`, while root/agent registration shares that operator key. Concurrent missions or registration retries can race on nonce and same-agent balance, duplicate a top-up or replace/conflict with registration transactions. Expose a writer funding method that locks the same operator address across balance check, send and confirmation; recheck balance inside the lock and require successful receipt. Cross-process operator sharing needs durable nonce coordination or explicit single-writer deployment.

Focused regression list: root duplicate with changed owner/expiry; revoked and expired root retry; exact valid root reuse; agent duplicate changed expiry; expired agent; failed-send catch observing revoked/wrong-root/different-expiry agent; valid matching racing registration; inconsistent rootLabel/rootNode rejects without transaction; two simultaneous funding requests yield one top-up; funding concurrent with registration obtains distinct serialized nonces; finalized/latest missing status or receipt grant; stale latest timestamp; future-skew timestamp; chain head advancement during pinned read.
