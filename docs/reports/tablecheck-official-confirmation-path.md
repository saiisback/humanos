# TableCheck official confirmation path — September 27, 2026

Scope: first-party TableCheck documentation only. This supplements [the venue contract inspection](tablecheck-contract-2026-09-27.md); no booking, account creation, authenticated API call, or live write was made.

## Documented guest path

1. The diner selects date, time, party size and plan, enters required details, then proceeds to a **review/confirmation step**. If the venue requires a card, card fields appear. The diner must then click **CONFIRM** within the displayed time limit. TableCheck says the completed reservation produces a subsequent confirmation page and confirmation email. Thus an initial form POST or an intermediate review screen alone is not proof of a booked table. [How to Make a Reservation](https://support-diners.tablecheck.com/hc/en-us/articles/900000972966-How-to-Make-a-Reservation)
2. The completed reservation's confirmation page can show restaurant, date/time, party size, **status**, orders and **Reservation ID**. The confirmation email also carries the Reservation ID; an optional SMS links to reservation details. A **downloadable receipt** and payment details appear only where applicable, according to restaurant settings. The Reservation ID and final status are useful booking evidence; a payment receipt is conditional and should not be required for a table-only booking. [How to Check Your Reservation](https://support-diners.tablecheck.com/hc/en-us/articles/900000872863-How-to-Check-Your-Reservation), [How to Check Your Reservation ID](https://support-diners.tablecheck.com/hc/en-us/articles/20368665739161-How-to-Check-Your-Reservation-ID)
3. TableCheck lists distinct reservation statuses, including Tentative, Unconfirmed, Accepted and Confirmed. Receipt extraction must preserve the observed status rather than equate the existence of an ID or page with `Confirmed`. [Reservation Status](https://support-diners.tablecheck.com/hc/en-us/articles/15633977395865-Reservation-Status)
4. A one-time password may be required for **3-D Secure cardholder authentication** when a booking involves card entry. TableCheck says failure to complete it can mean the reservation was not created. The official material inspected does not establish a universal reservation-specific OTP step for bookings without card authentication. [Resolving 3-D Secure Authentication Failures](https://support-diners.tablecheck.com/hc/en-us/articles/37527931413273-Resolving-3-D-Secure-Authentication-Failures), [Common Errors](https://support-diners.tablecheck.com/hc/en-us/articles/43650319150873-Common-Errors-When-Making-a-Reservation-and-How-to-Resolve-Them-Error-Summary)

## API and test-access facts relevant to verification

- Web Booking v1 keeps the actual guest booking on TableCheck's hosted page. Its API is read-only and can query completed reservations. It supports an optional `reservation_ref` supplied with `utm_source`, and the Sync API can notify an integrator after successful booking. These are possible **authorized integration** reconciliation routes, not a contract for the public page's `/reserve/create` response. [Web Booking v1](https://tablecheck.atlassian.net/wiki/spaces/API/pages/48595292/Web%20Booking%20v1), [Sync v1](https://tablecheck.atlassian.net/wiki/spaces/API/pages/44631150)
- TableCheck says its API has only a **production endpoint**, but its team can provision separate Test and Live **accounts** and test data. Access is reviewed through the API Portal; credentials and test environments become available after approval. This is not evidence of a publicly writable sandbox or of current project credentials. [Getting Started](https://tablecheck.atlassian.net/wiki/spaces/API/pages/44630975/Getting%2BStarted), [Requesting API Access](https://tablecheck.atlassian.net/wiki/spaces/API/pages/44729064/Request%2BAPI%2BAccess)
- The Distribution API is a different integration: native reservation creation with menu selection, no payments, and an access grant. Its `POST /reservations` flow requires a Blockage ID. This does not describe the Brooklyn Parlor hosted form's creation response. [Booking APIs](https://tablecheck.atlassian.net/wiki/spaces/API/pages/4687527943/Booking%2BAPIs), [Distribution v1](https://tablecheck.atlassian.net/wiki/spaces/API/pages/4637950094)
